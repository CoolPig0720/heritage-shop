# 后端系统设计与实现说明

（基于 Spring Boot + MyBatis-Plus）

---

## 一、后端总体设计

### 1.1 后端设计目标

后端系统主要负责：

1. 提供统一的业务接口服务（RESTful API）
2. 实现用户认证与多角色权限控制
3. 管理非遗商品、文化内容及定制流程数据
4. 对接第三方智能定制服务（大模型生图能力）
5. 保证系统数据的安全性、一致性与可扩展性

---

### 1.2 后端技术选型

| 技术                       | 用途说明              |
| ------------------------ | ----------------- |
| Spring Boot              | 后端主框架，负责业务逻辑与接口实现 |
| Spring MVC               | 构建 RESTful API    |
| Spring Security + JWT    | 用户认证与权限控制（无状态）     |
| MyBatis-Plus             | 数据持久层访问（Mapper/Service） |
| MySQL                    | 关系型数据库            |
| Redis                    | 缓存与扩展能力支撑（可选）      |
| Knife4j / OpenAPI        | 接口文档与调试             |
| 腾讯云 Java SDK（AIART）      | 智能定制（腾讯混元 AI 生图）对接 |
| JSON                     | 前后端数据交互格式         |

---

### 1.3 关键配置约定

后端主要配置集中在 `application.yml`：

* JWT 配置：`jwt.secret`、`jwt.expiration`
* 文件上传根目录：`file.upload.path`（默认 `uploads`）
* 文件公网访问基址：`file.public-base-url`（图生图在部分模式下需要可公网访问的参考图 URL）
* AI 生图（腾讯混元 / 腾讯云 AIART）：`ai.tencentcloud.secret-id`、`ai.tencentcloud.secret-key`、`ai.tencentcloud.region`（可选）、`ai.tencentcloud.endpoint`（可选）
* Redis（可选）：`spring.data.redis.*`（项目已提供 RedisTemplate 与缓存能力开关）

生产环境建议通过环境变量注入密钥类配置，避免在配置文件中明文写入。

## 二、后端整体架构设计

### 2.1 分层架构设计

后端采用典型的**分层架构模式**，各层职责清晰，避免业务逻辑混乱。

```
Controller 层（接口层）
        ↓
Service 层（业务逻辑层）
        ↓
Repository / Mapper 层（数据访问层）
        ↓
MySQL 数据库
```

#### 各层职责说明

* **Controller 层**

  * 接收前端请求
  * 参数校验
  * 返回统一格式的响应数据

* **Service 层**

  * 处理核心业务逻辑
  * 进行权限和业务规则判断
  * 调用数据访问层或第三方服务

* **Repository / Mapper 层**

  * 负责数据库 CRUD 操作
  * 不包含业务逻辑

## 三、后端包结构设计（非常重要）

### 3.1 推荐包结构

```text
com.heritage
├── controller        // 接口层
├── service           // 业务层
│   └── impl
├── mapper            // 数据访问层（MyBatis-Plus）
├── entity            // 实体类
├── dto               // 数据传输对象
├── config            // 配置类
├── security          // 权限与认证相关
├── common            // 通用返回、工具类
└── HeritageApplication.java
```

> 📌 这个结构**非常适合 Trae / AI 编程**，也非常“老师眼熟”。

## 十二、智能定制模块（后端设计）

### 12.1 模块职责

* 接收用户定制需求
* 转换为智能生成参数
* 调用第三方大模型接口
* 返回生成结果
* 保存历史生图记录（用于用户查看）

---

### 12.2 定制流程后端设计

1. 接收用户输入参数
2. 校验参数合法性
3. 组装定制请求数据
4. 调用大模型生图接口（文生图 / 图生图）
5. 保存历史记录（ai_image_record）
6. 返回生成图片信息

### 12.3 历史生图记录设计

#### 12.3.1 表设计（ai_image_record）

用于“用户历史记录”展示，字段只保留用户视角必要信息，避免与模型参数强耦合：

* id
* user_id
* original_image_url（可空，图生图参考图）
* prompt（可空）
* result_image_url（必填）

#### 12.3.2 结果图存储策略

考虑第三方返回的临时 URL 可能很长且不稳定，后端会将结果图落盘到本地 uploads 目录后再写库：

* 参考图：/uploads/ai-history-ref/...
* 结果图：/uploads/ai-history-result/...

该方式可避免数据库字段长度限制导致的写入失败，并保证历史记录可长期访问。

当图生图需要将“参考图”以公网 URL 方式提供给第三方时，后端会额外将参考图落盘到：

* /uploads/ai-ref/...

并要求配置 `file.public-base-url`，用于拼接可公网访问的参考图 URL。

#### 12.3.3 接口设计（核心）

* POST /api/customize/ai-image/text-to-image：文生图
* POST /api/customize/ai-image/image-to-image：图生图（multipart/form-data）
* GET /api/customize/ai-image/records：分页查询当前用户历史记录
